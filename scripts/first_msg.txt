The Product

An AI-generated branded proposal microsite platform. Freelancers and small agencies (India-first, primary segment: small digital marketing/AI agencies, 2-15 people) currently create client proposals inconsistently — anything from a plain WhatsApp message to a branded PDF, with no repeatable process. This product lets them describe a deal in plain language, have an AI ask follow-up questions until the details are complete, then generate a branded, hosted, shareable proposal webpage — replacing the PDF/Doc/WhatsApp status quo.

Core Product Decisions (do not relitigate these — they were deliberately decided)
Business model: Free tier (1 active proposal) + pay-per-proposal for occasional users + monthly subscription for frequent agency users.
Payments: UPI QR code + payment link, display-only. No live payment gateway, no confirmation/verification workflow — the product shows payment info, it does not track or verify payment status. Do not build a confirmation table or review step for this.
Currency: INR-only for v1. No multi-currency logic.
Domain routing: Subpath-based (domain.com/p/[slug]). No custom domain/CNAME support in v1.
Hard architectural constraint: Everything must be modular — new features attach without breaking changes to existing features, and no change may risk destabilizing production. This is why the data model is account-based (not user-based) from day one, even though team collaboration itself is a v2 feature.
Explicitly deferred to v2, do not build now: team collaboration UI (invites/roles/shared editing), MCP/AI-agent-attachable integration, live payment gateway (Razorpay), multi-currency, full version history/rollback, formal e-signature.
Brand Kit — Specific Quality Bar

Brand Kit extraction (from a URL) must use a headless browser (e.g. Playwright) to read computed CSS values directly from the live rendered page — actual color and font-family values, not guessed from raw HTML or a static screenshot. This accuracy bar is non-negotiable per the founder's explicit instruction. Also support brand extraction from an uploaded image/document (AI vision read) and manual color entry as alternative sources. Brand Kit setup happens once per account, before a user's first proposal, and is skippable but shows an honest disclaimer about reduced output quality if skipped. Brand Kits are also downloadable/exportable by the user for their own use outside this product.

Templates

Stored as structured data in the database (a templates table with a structure jsonb field defining sections and style tokens), not hardcoded in code — this is required by the modularity constraint, so new templates can be added without a deploy.

Database Schema (already finalized — build exactly this for Sprint 1)
accounts (id, name, default_payment_info jsonb, created_at)
users (id, account_id, role)
brand_kits (id, account_id, source_type enum['url','image','document','manual'], source_reference, colors jsonb, fonts jsonb, logo_url, timestamps)
templates (id, name, category, structure jsonb, is_system_default boolean, account_id nullable)
proposals (id, account_id, brand_kit_id nullable, template_id, status enum['DRAFT','PUBLISHED','ARCHIVED'], content jsonb, payment_info jsonb nullable, slug unique, timestamps)
credit_transactions (id, account_id, transaction_type enum['GRANT','DEDUCT'], amount, proposal_id nullable, created_at) — append-only ledger, this is the source of truth for billing, never a mutable balance column
Security Requirements

Row-Level Security enforced at the database level:

proposals: public/anon role can SELECT only where status = 'PUBLISHED'. Authenticated users can access only rows where account_id matches their own account.
brand_kits, credit_transactions: authenticated users only, own account only, no public access.
templates: public/anon and authenticated can read is_system_default = true rows; authenticated users can additionally access their own account's custom templates.
