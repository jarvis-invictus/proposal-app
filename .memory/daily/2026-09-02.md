## Key finding: brand kits were 100% cosmetic before this session
Colors/fonts were extracted (GPT-4o for text/image, Playwright scrape for URL) and persisted,
but grepping both AI routes for brand/color/font/logo/theme/kit returned zero matches — none of
it ever reached a prompt. "Reuse existing kit" wasn't a real feature, just an accidental side
effect of `ORDER BY created_at DESC LIMIT 1` at proposal-creation time with no UI ever surfacing
it. Separately, `styleReference` (the "match a past proposal" feature) only ever reached the
chat phase — it died at the boundary into `/api/generate-proposal`, which received only a
`summary` string. Both fixed in PR #39.

## Phase A shipped this session (PR #39, branch `feat/brand-aware-generation` off `main`)
- New `lib/accountContext.ts` (`getAccountContext()`), `lib/brand-extraction/prompt.ts`
  (`resolveBrandKit`/`brandContextBlock`), `lib/generation/promptBlocks.ts`
  (`styleReferenceBlock`/`briefBlock`) — shared helpers, reused by both AI routes.
- `lib/ratelimit.ts` split into two Upstash buckets (`chat` 15/10m, `generate` 6/10m) keyed by
  account id with IP fallback, replacing one shared 5/10m IP-keyed bucket.
- Intake screen (`NewProposalClient.tsx`) now shows "Using your saved brand kit '<name>'" with a
  `SelectMenu` switcher when >1 kit exists; a new optional "style or tone brief" textarea in the
  review modal threads through to generation.
- `app/api/proposals/route.ts` accepts a server-verified `brandKitId` instead of independently
  re-deriving "most recent" a second time with a different ordering than `new/page.tsx` used
  (`created_at` vs `updated_at` — a real latent bug, now unified on `updated_at`).
- Verified live against the **local Docker Supabase** (not production — `.env.local` still
  points to local Docker per the standing note below) with both zero-kit and one-kit accounts:
  confirmed via direct Postgres query that a generated proposal's `brand_kit_id` matches exactly
  the kit the banner showed, and that the new brief field ("warm and playful") visibly shaped
  generated package description tone.

## New gotcha for future sessions
This browser automation tool's `navigate` intermittently lands on the wrong page (once hit
`/login`, once hit `/dashboard` instead of the requested `/proposals/[id]/edit` URL) even though
the session and route are both fine — confirmed by immediately retrying the identical direct
navigation and landing correctly. Don't conclude "auth broke" or "route broke" from one flaky
nav; retry once before treating it as a real bug. (Consistent with the existing documented click
gotcha in `MEMORY.md` — this tool's interaction layer is generally unreliable, not just clicks.)
