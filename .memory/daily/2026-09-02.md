## Key finding: brand kits were 100% cosmetic before this session (Phase A)
Colors/fonts were extracted (GPT-4o for text/image, Playwright scrape for URL) and persisted,
but grepping both AI routes for brand/color/font/logo/theme/kit returned zero matches — none of
it ever reached a prompt. "Reuse existing kit" wasn't a real feature, just an accidental side
effect of `ORDER BY created_at DESC LIMIT 1` at proposal-creation time with no UI ever surfacing
it. Separately, `styleReference` (the "match a past proposal" feature) only ever reached the
chat phase — it died at the boundary into `/api/generate-proposal`. Both fixed in PR #39: new
`lib/accountContext.ts`, `lib/brand-extraction/prompt.ts`, `lib/generation/promptBlocks.ts`;
`lib/ratelimit.ts` split into two account-keyed buckets (chat 15/10m, generate 6/10m) replacing
one shared 5/10m IP-keyed bucket. Verified live against local Docker Supabase with both zero-kit
and one-kit accounts — a generated proposal's `brand_kit_id` matched exactly the kit the new
intake banner showed, confirmed by direct Postgres query, not just the UI.

## Phase B shipped this session (PR #40, branch `feat/animated-presentation-deck` off `main`)
New `framer-motion` dependency (this repo had zero animation libraries before this). New
`components/presentation/DeckView.tsx` — a full-screen, slide-by-slide animated presentation
derived at render time from the same `content` JSON the static document renders
(`lib/presentation/buildDeck.ts`) — no parallel AI schema. It's a sibling to the static document,
never a replacement: signing/PDF export/audit-trail stay exclusively on the static
`PublicProposalView`, which stays the default for shared links. Reachable via a "View as deck"
toggle on the public page, "Preview as deck" in the Editor header, or `?view=deck`.

**Bug found and fixed during live testing**: grid columns using bare `1fr` (not `minmax(0,1fr)`)
don't shrink below their content's intrinsic width — combined with the deck's centered layout,
this pushed slide content off-screen to the left at mobile widths. Fixed in `DeckView.tsx`.

**Unresolved, flagged but NOT fixed (out of scope for PR #40)**: while narrowing the browser
tool's viewport to test the above, the *pre-existing, untouched* static document view
(`PublicProposalView.tsx`, e.g. its `<h1>` header) showed the exact same left-clipping symptom
at the same narrow width — confirmed by testing before touching any of my new code. This means
either (a) a real, pre-existing narrow-viewport bug somewhere in this app's shared layout/CSS
that predates this session, or (b) an artifact specific to this dev environment's browser-pane
viewport emulation (plausible — dimensions reported via `getBoundingClientRect` were internally
inconsistent with the actual CSS width in a way that only reproduced under mobile-preset
emulation, not at 1280px+). Did not chase further since it's unrelated to Phase B's scope and
reproduces on code this session never touched — worth a dedicated look if real mobile users ever
report a public-proposal-link display issue.

## New gotcha for future sessions
This browser automation tool's `navigate` intermittently lands on the wrong page (hit `/login`
once, `/dashboard` once, plain `404` twice) even though the session and route are both fine —
confirmed every time by immediately retrying the identical direct navigation and landing
correctly. Don't conclude "auth broke" or "route broke" from one flaky nav; retry once. Also: a
long-running `next dev --turbopack` process can get stuck serving a stale/broken intermediate
compile after several rapid file edits (hit a phantom "duplicate variable" error that didn't
exist in the actual file on disk) — killing and restarting the dev server process cleared it.
(Consistent with the existing documented click gotcha in `MEMORY.md` — this tool's interaction
layer and this framework's long-lived dev server are both generally less durable than they look.)
