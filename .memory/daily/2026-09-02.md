## Key finding: brand kits were 100% cosmetic before this session (Phase A)
Colors/fonts were extracted (GPT-4o for text/image, Playwright scrape for URL) and persisted,
but grepping both AI routes for brand/color/font/logo/theme/kit returned zero matches — none of
it ever reached a prompt. "Reuse existing kit" wasn't a real feature, just an accidental side
effect of `ORDER BY created_at DESC LIMIT 1` at proposal-creation time with no UI ever surfacing
it. Separately, `styleReference` (the "match a past proposal" feature) only ever reached the
chat phase — it died at the boundary into `/api/generate-proposal`. Both fixed in PR #39: new
`lib/accountContext.ts`, `lib/brand-extraction/prompt.ts`, `lib/generation/promptBlocks.ts`;
`lib/ratelimit.ts` split into two account-keyed buckets (chat 15/10m, generate 6/10m).

## Phase C shipped this session (PR #41, on top of Phase A)
`/api/generate-proposal` now runs four parallel `generateObject` calls (header, packages+add-ons,
timeline, terms+payment — all `ProposalSchemaV1.pick(...)`, no new AI schema) instead of one,
assembled in code with directly-computed dates. A critique pass (`lib/generation/critique.ts`)
reviews the assembled draft and returns advisory findings — shown once as a dismissible Editor
banner via `sessionStorage`, never persisted. Objective pricing bugs (`originalPrice <=
discountedPrice`) are auto-corrected in code (`lib/generation/pricing.ts`), never surfaced as an
AI opinion — this resolves the block-vs-flag question left open in `PHASE2_INITIATIVES_PLAN.md`.
The chat tool's dead `isComplete` self-report is replaced by a real `facts` object + a
deterministic `assessCompleteness()` check run client-side.

**Live-tested against real GPT-4o calls, twice, not mocked**: both runs produced genuinely useful
critique findings — a fabricated `originalPrice` not grounded in the deal summary (both times,
consistently, a real recurring model behavior worth knowing about), invented payment terms after
the user explicitly said none were set, and a subtle fixed-price-vs-hourly-billing inconsistency
a human reviewer could plausibly miss. Also caught and fixed a real prompt-quality issue live:
the critique initially flagged the app's own deterministically-computed dates as suspicious on
every single run (pure noise) — one added instruction line fixed it, confirmed on the next run.
Verified directly in Postgres (not just the UI) that `_critique` never leaks into persisted
`content` on either run, and that the banner is genuinely one-time (dismissed, reloaded, gone).

## New gotchas for future sessions
- This browser automation tool's `navigate` intermittently lands on the wrong page (`/login`,
  `/dashboard`, plain `404`) even though the session and route are both fine — confirmed every
  time by immediately retrying the identical navigation. Retry once before concluding a real bug.
- A long-running `next dev --turbopack` process can get stuck serving a stale/broken intermediate
  compile after several rapid file edits (a phantom "duplicate variable" error that didn't exist
  in the actual file on disk) — kill and restart the process.
- **Local dev infra can silently go stale between sessions**: Colima (the Docker runtime) and the
  local Supabase stack were both down at the start of Phase C testing, and the installed
  `supabase` CLI (2.34.3) was far enough behind the repo's `supabase/config.toml` schema
  (generated by a newer CLI) that `supabase start` refused to parse it. Fixed by `colima start`,
  `brew upgrade supabase` (needed `brew trust supabase/tap` first — Homebrew's tap-trust gate),
  then `supabase start` — DB data survived intact (12 proposals, unaffected). If `/login` or
  "could not sign up" errors show up unprompted at the start of a session, check `docker ps` /
  `colima status` before assuming an app-level auth bug.
